# План: Aptiloop Usability Release (перенос курсов, установка/запуск, обновления, ошибки импорта, промпты, версионирование курсов)

## Context

Запрос Ян: довести Aptiloop до удобной рабочей версии для одного локального пользователя (Core Alpha, без аккаунтов/синка/маркета). Нужно: (1) экспорт/импорт курсов в двух форматах — «поделиться паком» и «перенос N курсов с прогрессом на другой ПК»; (2) кроссплатформенные (Windows/macOS/Linux) установка и запуск в духе opencodex — `npm install -g`, CLI `aptiloop`, без Electron и без десктоп-обёртки (веб-морда остаётся как есть); терминал после запуска закрывается; автозапуск настраивается и из Settings, и дублем из CLI; трей — позже, в этом плане его нет; порты по умолчанию не мешают пользователю (уйти с 3000) и конфигурируются; (3) обновление приложения из GitHub Releases через интерфейс и через CLI в духе ocx, плюс задел под серверный сценарий в духе dokploy; (4) конкретные actionable-ошибки импорта пака (сейчас «2 ошибки» без деталей) с кнопкой «скопировать для ИИ»; (5) переработка промптов/скилла создания курсов: упростить ввод и добавить instructional-design слой по 10 пунктам обратной связи, не ослабляя schema/security/validation; (6) версионирование/обновление курса без пересоздания, с выбором для пользователя. Решения Ян: перенос — два формата; обновления — канал GitHub Releases; обновление курса — диалог с выбором (по умолчанию «новая ревизия с сохранением прогресса»); установщик — терминальный/npm-стиль opencodex, GUI-инсталлер не нужен.

## Approach

### Шаг 1. Контракты переноса: share-pack vs transfer-with-progress (база всего остального)

- Ввести два строго разделённых формата переноса на уровне `packages/shared` + `packages/database` + `apps/orchestrator`:
  - `share`: ровно один канонический Course Pack (`aptiloop.course-pack`, как сейчас отдаёт `exportCanonicalJson`). Без истории, без приватного. Идентичен тому, что ставится через существующий import.
  - `transfer`: конверт «курс(ы) + прогресс» для смены ПК: `{ manifest, packs[], learnerScope }`. `packs[]` — канонические паки выбранных курсов/ревизий; `learnerScope` — только replayable-факты: adaptation-branch привязки, Learning Kernel facts (evidence/progress/correction/review), derived-projection контрольные точки (пересчитываются при импорте, не доверяем вслепую), review items/mistakes как проекции (перестроить из фактов при импорте), session snapshots-ссылки. Явно исключить: credentials, env-файлы, exercise workspaces (только manifest-ссылки на trusted template ID), абсолютные/UNC/device пути, transient provider capability state, логи. Переиспользовать санитизацию из `data-portability.ts` (portable-profile-v1 policy: excludes, managed-provider правила, проверка абсолютных путей) — нового санитайзера не писать, расширить существующий новым `scope: course-transfer`.
- Правила: размер/число/глубина лимиты как у паков (переиспользовать `COURSE_PACK_JSON_LIMITS_V1` + новый лимит конверта, напр. 64 МБ дефолт, точное число фиксирует имплементация в schema-константе и показывает в UI до экспорта); неизвестные поля/версии — fail closed; импорт идемпотентен по `operationId`; невалид — в quarantine с диагностикой (как сейчас `recordQuarantine`).
- Совместимость: существующий `GET /api/course-packs/export?revisionId=` и `POST /api/course-packs/validate` + `.../validations/:id/commit` не ломать; transfer — новые маршруты `POST /api/course-transfer/export`, `POST /api/course-transfer/validate`, `POST /api/course-transfer/validations/:id/commit`, `GET /api/course-transfer/validations/:id`. Оба экспорта требуют явного действия пользователя с именованным scope (какие курсы, с прогрессом или без) — privacy-инвариант «explicit user action naming destination and scope».

### Шаг 2. UI + CLI переноса (share и multi-course transfer)

- Courses/Library: к каждому курсу кнопки «Поделиться паком» (скачивание `.course-pack.json` через существующий export) и «Перенести с прогрессом» (чекбоксы выбора 1..N курсов + переключатель «включить историю» + показ размера/состава до скачивания). Import-страница принимает оба типа файлов, автоопределяет тип по `format` и ведёт по нужному validate→Preview→commit флоу; Preview для transfer показывает: курсы, ревизии, объём истории (число facts/sessions), что исключено (credentials/пути), конфликты (курс уже есть → отсылка к шагу 7).
- CLI (новый `aptiloop`, см. шаг 3) обязательно дублирует: `aptiloop courses export --course <key> [--with-progress] [--out file]`, `aptiloop courses import <file> [--dry-run]`, `aptiloop courses list`. Никакой новой логики в CLI — только тонкий вызов тех же orchestrator-маршрутов.
- Пустые/конфликтные случаи: нет курсов → honest empty state; файл чужого формата → «не transfer/пак, детали в диагностике»; существующий курс+ревизия → идемпотентный «уже установлено», новая ревизия того же courseKey → диалог апгрейда из шага 7.

### Шаг 3. CLI `aptiloop` в духе `ocx`: установка через npm, foreground/background, закрываемый терминал

- Образец — opencodex (`npm install -g @bitkyc08/opencodex`, `ocx start` foreground на `localhost:10100`, `ocx service` для фона через launchd/systemd/Task Scheduler, `ocx gui`, `ocx status/health/ready`, `ocx update`, `ocx uninstall`). Тот же UX, адаптированный к двум сервисам Aptiloop (пользовательский web + внутренний orchestrator).
- Дистрибуция: публикуемый npm-пакет с `bin: aptiloop`, содержащий собранные web+orchestrator артефакты и CLI (исходник CLI — новый `packages/cli`, тонкая обёртка без доменной логики; такого пакета сейчас нет — unverified, подтвердить отсутствием `packages/cli` перед стартом). Установка: `npm install -g aptiloop` (Node >=24 по engines; без bundled runtime — в отличие от ocx/Bun, у нас чистый Node). Из исходников: `git clone`, `npm ci`, `npm run build`, затем `npm link` или `npx aptiloop`. Никаких новых пакетных менеджеров, GUI-инсталлера и Electron в этом плане нет.
- Фиксированный набор команд (`aptiloop --help` обязан перечислять все — это контракт): `init` (первый запуск: проверка Node/портов, сборка если надо, выбор data dir, печать URL и следующих шагов); `start [--port N] [--orch-port M] [--open]` (foreground; печатает URL, версию, PID; Ctrl+C гасит дерево); `stop`; `status [--json]` (`{running, web, orchestrator, version, pid, ports}`); `health` / `ready [--wait]` (liveness/readiness обоих сервисов; exit-коды как у ocx: 0 ready, 1 нет, 64 неверные аргументы); `open`/`gui` (открыть UI в браузере); `service install|start|stop|restart|status|uninstall [--autostart]` (фон, переживающий закрытие терминала); `autostart on|off|status` (дубль управления автозапуском поверх service; без установленного service — явная ошибка с подсказкой `service install`); `update check|apply [--version vX.Y.Z]`; `courses list|export|import` (шаг 2); `doctor` (порты, data dir, здоровье, пути артефактов — вложение в багрепорты); `uninstall` (stop + снять service/autostart/ярлыки, данные НЕ трогать; дальше обычное `npm uninstall -g`).
- Дополнение к списку команд шага 3 (часть того же контракта `--help`): `shortcuts install|remove` (ярлыки Desktop/Start Menu/Applications с целью `aptiloop open`; детали — шаг 4).
- Фон/закрытие терминала: `start` — всегда foreground; фон — только через `service` (как `ocx service`). Переиспользовать существующие `scripts/start-local.mjs` + `scripts/local-process-launcher.mjs` (production build plan + service plans) — service-обёртка вызывает те же plans, не дублирует их. Pidfile + логи — в `<dataDir>/runtime/` (`aptiloop.pid`, `web.log`, `orchestrator.log`); один pidfile-лок, повторный запуск — явная ошибка «уже запущено (pid N)».
- Data dir (обязателен для global-установки: у глобального пакета нет repo-относительного `.data`): порядок — `--data-dir` > `APTILOOP_DATA_DIR` > ОС user-data (`%APPDATA%/Aptiloop` / `~/Library/Application Support/Aptiloop` / `~/.local/share/aptiloop`) > repo `.data` только в source-checkout. `init` показывает выбранный путь и предлагает перенести существующий `.data` через transfer-файл шага 1, никогда молчаливым копированием.
- Порты: пользователю виден ОДИН порт — web UI. Дефолты: web `10101` (уйти с конфликтного 3000; рядом с ocx-стилем, но не занимать чужой 10100), orchestrator остаётся `8787` (уже нестандартный; смена тянет широкий blast radius без пользы). Конфиг: `--port/--orch-port` > `APTILOOP_PORT/APTILOOP_ORCHESTRATOR_PORT` > дефолт; обе службы — только loopback (инвариант не менять). Явно указанный занятый порт — fail closed «порт N занят, укажите --port»; silent port-hopping запрещён. Смена дефолта web-порта — contract change одним коммитом: обновить `apps/web/orchestrator-url.ts` (default), `apps/orchestrator/src/app.ts` (defaultWebOrigin), `scripts/local-process-launcher.mjs` (plans+env), `Dockerfile`/`compose.yaml` (публикация), `SELF_HOSTING.md`, тесты `start-local.test.mjs`/`orchestrator-url.test.ts`/e2e-дефолты — точный список даёт `grep 3000`. Settings показывает текущие порты и data dir read-only + подсказку смены через CLI/env; редактирования портов из UI в этом плане нет (смена требует рестарта вне живого процесса).

### Шаг 4. Автозапуск и ярлыки кроссплатформенно (трей — позже, в плане его нет)

- Трей по решению Ян НЕ делаем вообще (ни companion-процесса, ни пункта в Settings кроме честной строки «трей — позже»). Шаг закрывается связкой service + autostart + shortcuts.
- Фон-сервис по ОС — та же таблица, что у ocx: macOS launchd, Linux systemd user unit, Windows Task Scheduler (hidden). `service install` кладёт unit `Aptiloop`, запускающий `aptiloop start` с зафиксированными портами/data dir момента установки (смена — через reinstall); `uninstall` снимает всё. Только user-level: никаких SYSTEM-служб/daemon-root. Windows — фиксированный `schtasks /Create /TN Aptiloop /TR "...aptiloop start" /SC ONLOGON` (shell:false, timeout, без пользовательских argv); macOS — `~/Library/LaunchAgents/aptiloop.plist` (RunAtLoad по флагу --autostart); Linux — `~/.config/systemd/user/aptiloop.service` + `systemctl --user enable/disable`. Автозапуск = `service install --autostart` / `autostart on` (enable) / `autostart off` (disable без uninstall); та же операция — тоглом в Settings.
- Все ОС-мутации исполняет только orchestrator-owned модуль (shell:false, фиксированный план, timeout, process-tree cleanup); браузер шлёт только `{ autostart: bool }` + operationId. Settings показывает фактическое состояние (unit exists/enabled — проверять в ОС, не верить флагу) и кнопки вкл/выкл. Ярлыки (Desktop/Start Menu/Applications: .lnk/.desktop по ОС, цель `aptiloop open`) — команда `aptiloop shortcuts install|remove` и дубль-кнопка в Settings; иконка — существующий `apps/web/app/icon.svg`.
- Первый-run сценарий из запроса: `npm i -g aptiloop`, `aptiloop init`, `aptiloop service install --autostart`, `aptiloop service start`, открыть UI, закрыть терминал — всё продолжает работать; дальше автозапуск/обновления — из Settings или CLI.

### Шаг 5. Обновления из GitHub Releases через UI и CLI (+ задел под серверный профиль)

- Релизный конвейер (CI workflow `release.yml` на tag `v*`): сборка web+orchestrator артефактов, `THIRD_PARTY_NOTICES`+SBOM (CycloneDX) как в supply-chain job, `SHA256SUMS`-манифест, GitHub Release с changelog. Источник версии: корень `package.json` + новый `GET /api/version` (app version, validator version, migration ledger head, channel `github-releases`, deployment profile `source-checkout|compose`).
- Проверка/применение: кнопка Settings «Проверить обновления» + `aptiloop update check` дергают Releases API (только явное действие или редкий poll, не скрытая телеметрия); UI показывает версию, changelog, размер, требуемую миграцию. Скачивание — сверка SHA-256 с манифестом релиза поверх TLS (минимум; подпись cosign/sigstore — если дешево ляжет в workflow, иначе следующим шагом). Применение: approved backup БД (`db:backup` в `.data/approved-backups`, non-overwriting) → stop → замена артефактов → `db:migrate --authorize-current --approved-backup ... --backup-sha256 ...` → health/ready → успех/rollback (предыдущие артефакты + откат БД whole-file к cutoff, failed-БД сохраняется отдельно — как в SELF_HOSTING). Никакого silent auto-update и никакого fallback на «частичное обновление».
- CLI-паритет: `aptiloop update check`, `aptiloop update apply [--version vX.Y.Z]`. Терминальный путь обязан работать без браузера.
- Серверный задел (пока loopback-only, без auth — НЕ добавлять публичный self-hosting в этом плане): updater учитывает `deployment profile`: в `compose`-профиле — обновление образов + paired backup `harness-data`+`harness-attempts` по процедуре SELF_HOSTING (stop, cold copy, verify, candidate volumes), без копирования compose-БД в process-mode путь. Публичные auth/TLS/изоляция — явно не в скоупе, докладывать в UI предупреждением как сейчас.

### Шаг 6. Actionable-ошибки импорта: точный код + путь + что править + «скопировать для ИИ»

- Корень проблемы: UI показывает только групповое предложение (`courses.validation.diagnostic.*` — 7 generic-строк), а сервер присылает точные `code/path/entityId/ruleId/context/message`, которые presentation-слой отбрасывает для неизвестных групп (`generic`). Плюс стейджинг режет отчёт до 100 диагностик/64 КБ без пометки truncation.
- Исправить: `presentCoursePackDiagnostic` возвращает полную точную карточку: `code` (напр. `PACK_SHAPE_INVALID`), `path` (JSON-pointer), `entityId`, `ruleId`, исходный `message` валидатора (он уже bounded/safe; secret-фильтр `secretLikePattern` сохранить), а групповая i18n-строка становится подзаголовком, не заменой. `DiagnosticList` в `course-pack-client.tsx`: каждая строка — badge кода + моноширинный path + entity + человекочитаемый message + per-code fix-подсказка («что править в draft JSON») + кнопка «Скопировать для ИИ» (копирует markdown: code/path/message/section-подсказку для вставки в генератор курса) + кнопка «Скачать diagnostics JSON». Каталоги `en-US`/`ru-RU` дополнить fix-строками для частых кодов (SHAPE/DRAFT_SHAPE, CONTENT_HASH_MISMATCH, graph/reference/provenance/requirement/locale), остальные — generic fix «покажи это сообщение модели вместе со snippet вокруг path».
- Сервер: в `boundedStagedReport`/`stagedValidationResponse` добавить `totalErrors/totalWarnings/truncated` — UI при truncation честно пишет «показаны первые 100 из N». Важно для слабых моделей: копируемый текст обязан содержать всё нужное для ремонта без открытия кода (code+path+message достаточно; requirements/hashes руками не править — напомнить в fix-тексте, как в Layer 5 скилла).
- Ошибка «N errors» в заголовке превращается в «N ошибок: первая — <code> <path>», клик скроллит к списку.

### Шаг 7. Апгрейд курса без пересоздания: диалог из трёх вариантов, дефолт — новая ревизия с сохранением прогресса

- Триггер: импорт пака с тем же `course.courseKey`, но большим `revision.revisionNumber` (родительская связь `parentRevisionKey` валидна). UI-диалог предлагает (радио, дефолт — первый): (a) «Обновить: новая ревизия, прогресс сохранить» — install новой immutable-ревизии + rebase personal adaptation branch на новый base hash + replay kernel facts для уцелевших activity ID + дособрать review для изменённых нод; удалённые/поменявшие completion activities — историческая evidence read-only + `superseded`, mastery пересчитывается детерминированно (новая projection, старые facts не мутятся); (b) «Поставить рядом отдельным курсом» — install как новый Course (суффикс ключа показывает UI до коммита); (c) «Заменить с бэкапом» — сначала transfer-экспорт текущего (шаг 1), потом Course-scoped delete, потом install с нуля. Любой конфликт (occupied branch, смена primary locale, удалённые required activities без маппинга, active session на старой ревизии) — fail closed с объяснением и без частичной записи.
- Репозиторий: новый метод апгрейда рядом с `install` (не внутрь install-флагами): `upgradeCourseToRevision` в `CoursePackRepository` (+ personal-adaptations rebase + `LearningKernelRepository` replay), транзакционно, идемпотентно по operationId. Active session старой ревизии продолжает жить на пиннутом снапшоте (lesson-engine инвариант: сессия не мутирует от новой публикации); новые сессии — на новой ревизии.
- Упрощение создания (из запроса): Discovery — максимум 2 раунда сгруппированных вопросов + «использовать рекомендованное»; Proposal показывает assumptions trade-off (время interview-readiness vs engineering-capability) одной таблицей; кнопки Approve/Revise как сейчас.

### Шаг 8. Authoring skill: добавить Learning Design слой (10 пунктов), не трогая authority/security/validation

- Файл скилла `course-authoring-instruction.ts` (Layer 3 lifecycle + Layer 4 compilation rules) переписать так (Layer 1 identity/authority, Layer 5 repair-budget=3, Layer 6 embedded assets — не ослаблять ни строкой):
  1. После Discovery вставить обязательный `Learning Design` до Proposal: `target capability → observable evidence → practice → feedback → instruction/review`. Proposal без этого раздела — невалиден для компиляции (инструкция модели, не код).
  2. `Attempt-before-answer` как дефолт: сначала попытка learner (recall/решить/спроектировать), потом объяснение/reference, потом изменённый вариант, потом spaced review; «прочитал и понял» — не evidence.
  3. Классы decision-практики для SWE-курсов: декомпозиция, state ownership, public/private/shared, когда (не) создавать абстракцию, trade-offs допустимых решений, рефакторинг наивного решения, смена требований после реализации, debugging/perf investigation, чтение production-кода с альтернативами; цикл `naive → problem → observe → change → new trade-off`.
  4. Diagnostic-конфликт: требует brief → обязателен; отказ пользователя при известном level — фиксируется как explicit assumption в Proposal; молча пропускать запрещено.
  5. Placeholders: `[X]`/неизвестное — либо Discovery-вопрос, либо explicit unresolved, либо approved assumption в Proposal; тихая конкретизация («3–4 часа») запрещена.
  6. Capability mismatch: при пустых environmentIds/checkIds — явная деградация `runtime practice unavailable → recall/teacher-dialogue/code-reading/interview/checkpoint`, exercise НЕ authorить (контракт не ослаблять).
  7. Dual objective: `interview readiness` + `independent engineering capability` раздельно; конфликт по времени — показать trade-off в Proposal.
  8. Transfer-check: после паттерна — задача с изменёнными условиями (map/filter → Map/Set → streaming/async + «почему первое решение не подходит»).
  9. Mastery evidence: для skill/procedure-нод Proposal отвечает «что сможет без подсказки»; минимум 1 тип: reproduce-from-memory / novel-variant / causal-explain / diagnose-broken / design-under-constraints / defend-tradeoffs.
  10. Явно: валидация/схема/protected/provenance/stable IDs/approval gates — без изменений.
- Тот же контракт продублировать в in-app guided designer (порядок Brief→Discovery→Learning Design→Diagnostic→Proposal→Review) и в `prompt-library` `course-designer` prompt (текст, не схема). Версию скилла привязать к сборке (repositoryRevision уже есть; добавить `skillContentVersion`, mismatch скачанного скилла — warning в import Preview). Промпты короче не за счёт выкидывания запретов, а за счёт структуры и примеров «как надо».

## Verification

- Перенос: экспорт share→импорт на чистой БД (новая revision ставится, валидация зелёная); transfer 2 курсов с историей→импорт на чистой БД: kernel replay даёт те же projections (сравнить hash), prohibited-scan конверта (credentials/абсолютные пути/provider-sessions отсутствуют); злонамеренный конверт (лишний exec-фрагмент, неизвестная версия, переписанный hash) — reject + quarantine. Команды: `npm run typecheck`, `npm run test:fast`, `npm run test:e2e`, `npm run build`; CLI: `aptiloop courses export --with-progress` → `import --dry-run` → `import`.
- Запуск/ОС: чистая машина каждой ОС (Windows, macOS, Linux): `npm i -g aptiloop` → `aptiloop init` → `aptiloop start` печатает URL с портом 10101 и версию → `status` green → терминал закрывается только после `service install/start` (проверить: сервис жив после закрытия терминала); `stop` гасит дерево (нет висящих node); тоглы автозапуска в Settings и `autostart on|off` создают и снимают реальный unit/task (проверка средствами ОС: `systemctl --user status` / `launchctl list` / `schtasks /Query /TN Aptiloop`); занятый порт → явная ошибка с подсказкой --port. `npm run test:local-launch` зелёный.
- Обновления: тестовый pre-release в GitHub: Settings «Check» видит версию+changelog; `update apply` с неверной SHA — отказ без изменений; happy path: backup создан в `.data/approved-backups`, миграция авторизована, health green, rollback-путь проверен на disposable-БД (инвентарь + approved backup + migrate + rollback по SELF_HOSTING-процедуре).
- Ошибки: сломанный пак (shape + graph + provenance) показывает ≥3 точных карточек code+path+entity+fix; «Copy for AI» вставляет это в генератор и ремонт проходит за ≤3 раундов (бюджет Layer 5); truncated-отчёт на паке с >100 диагностиками пишет «первые 100 из N».
- Скилл: сгенерированный новым скиллом курс содержит Learning Design раздел, attempt-before-answer активности, dual-objective trade-off, transfer-вариант, mastery-evidence, ноль silent placeholders, ноль exercise при пустом registry; старый скилл на новом билде — warning о mismatch.
- Апгрейд: v1 с прогрессом → импорт v2: дефолтный путь сохраняет evidence (старые факты на месте, projection пересчитана), side-by-side и replace-with-backup работают из того же диалога; active session v1 догуляет на старом снапшоте.

## Assumptions & contingencies

- Решение Ян принято: канал обновлений — GitHub Releases (git-pull канала не делаем); перенос — оба формата; апгрейд курса — выбор из трёх с дефолтом (a). Если релиз-пайплайн задержится — временный ручной Release (залить артефакты руками по той же схеме имя/манифест/SHA) вместо отката к git-каналу: формат релиза фиксирован в этом плане.
- Трей в этом релизе отсутствует по решению (позже отдельным планом); в Settings — только честная строка-заглушка, никакого полу-трея. На CLI/установщик/апдейтер это не влияет.
- Если GitHub Releases API недоступен офлайн — updater честно показывает «не проверено», никакого silent-fallback и никакого Mock-обновления.
- Лимиты конверта (размер/число курсов) фиксирует имплементация в schema-константах и показывает в UI до экспорта; E2E `npm run test:e2e` — обязательный гейт, `npm run verify` его не заменяет.
